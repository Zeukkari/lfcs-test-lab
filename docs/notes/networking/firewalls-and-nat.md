# Networking — packet filtering and NAT (iptables, nftables)

Domain: Networking ("Configure packet filtering, port redirection, and
NAT").

## iptables fundamentals (tables, chains, rule lifecycle)

General refresher; the NAT-specific worked exercise is in the next
section.

### Tables and their built-in chains

| Table | Purpose | Built-in chains |
| --- | --- | --- |
| filter | accept/drop decisions (default table) | INPUT, FORWARD, OUTPUT |
| nat | address/port translation | PREROUTING, INPUT, OUTPUT, POSTROUTING |
| mangle | header alteration (TTL, marks) | all five |
| raw | pre-conntrack exemptions (NOTRACK) | PREROUTING, OUTPUT |

Packet paths (which chains a packet traverses):

- Arriving, destined to this host: `PREROUTING → INPUT → process`
- Routed through this host: `PREROUTING → FORWARD → POSTROUTING`
- Generated by this host: `OUTPUT → POSTROUTING`

This is the "why OUTPUT, not PREROUTING, for locally originated traffic"
rule from the NAT section, generalized.

### Rule anatomy

```bash
iptables -t filter -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -j ACCEPT
#         ^table   ^op+chain ^matches.................................. ^target
```

`-t filter` is implied when omitted. The target is a built-in verdict
(`ACCEPT`, `DROP`, `REJECT`, `LOG`), an extension (`DNAT`, `SNAT`,
`MASQUERADE` — nat table), or a custom chain name (a jump).

### Rule lifecycle operations

```bash
iptables -L -v -n --line-numbers    # list: counters, numeric, numbered
iptables -S INPUT                   # list as rule-spec lines (copy/paste-able)
iptables -A INPUT <rule>            # append (bottom)
iptables -I INPUT 1 <rule>          # insert at position (1 = top)
iptables -D INPUT 3                 # delete by number
iptables -D INPUT <full rule spec>  # delete by matching spec
iptables -R INPUT 2 <rule>          # replace rule 2
iptables -F INPUT                   # flush a chain (all chains if omitted)
iptables -N NAME / -X NAME          # create / delete custom chain
iptables -P INPUT DROP              # default policy (built-in chains only)
```

**First match wins** — rule order is the logic. `-I` vs `-A` placement
matters; use `--line-numbers` + `-I CHAIN <n>` for surgical placement.

### Common matches

```
-p tcp|udp|icmp
-s 10.0.0.0/8   /   -d 192.168.56.0/24
--sport / --dport                 (require -p)
-i eth0                           (ingress iface: INPUT/FORWARD/PREROUTING)
-o eth0                           (egress iface: OUTPUT/FORWARD/POSTROUTING)
-m conntrack --ctstate NEW,ESTABLISHED,RELATED,INVALID
-m multiport --dports 22,80,443
-m comment --comment "why this rule exists"
```

### The classic stateful INPUT recipe

```bash
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -i lo -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -j ACCEPT
iptables -P INPUT DROP
```

The order is the lockout-safety ritual: allow established + SSH
**first**, set the DROP policy **last**. Running `-P INPUT DROP` first
over an SSH session cuts you off instantly.

### REJECT vs DROP

- `DROP` — silent discard; client hangs until timeout
- `REJECT` — sends ICMP port-unreachable (or `--reject-with tcp-reset`);
  client fails fast. Friendlier inside trusted networks; DROP is common
  on internet-facing edges.

### Which backend am I on?

```bash
iptables -V
# iptables v1.8.10 (nf_tables)   <- shim translating into nftables
# iptables v1.8.10 (legacy)      <- classic x_tables backend
```

On the nf_tables backend, iptables-created rules actually live in the
nftables kernel engine (visible via `nft list ruleset`). Avoid managing
the same host with raw `nft` and `iptables` simultaneously — pick one
tool per task.

Persistence: see "Persisting iptables rules across reboot" in the NAT
section below.

## iptables NAT (custom chain, DNAT redirect, locally-originated traffic, ip_forward)

Domain: Networking ("Configure firewall rules" / NAT). Worked example
from an exercise:

> On node2, serve `/lfcs-nat-1.txt` on TCP 18601 with the exact content
> `NAT-1-NODE2`. On node1, using a nat-table chain named `LFCSNAT`,
> redirect locally originated TCP connections to `192.168.56.11:18601`
> onward to node2 `192.168.56.12:18601`, and enable IPv4 forwarding. A
> `curl` from node1 to `192.168.56.11:18601` must reach the node2
> backend.

### Part 1 (node2): serve exact file content on a TCP port

No real web server needed — a tiny one-shot/looping TCP listener is
enough for grading, as long as it returns exactly the requested bytes.

```bash
echo -n "NAT-1-NODE2" > /lfcs-nat-1.txt

# one-shot test (answers a single connection then exits)
nc -l -p 18601 < /lfcs-nat-1.txt

# or a simple HTTP-less raw-TCP responder that keeps serving:
while true; do nc -l -p 18601 < /lfcs-nat-1.txt; done
```

- `echo -n` is important — a trailing newline will make the content
  not match an "exact content" check (`NAT-1-NODE2\n` != `NAT-1-NODE2`).
- For something persistent across reboots/sessions, wrap it in a
  systemd service or `socat`:

  ```bash
  socat TCP-LISTEN:18601,reuseaddr,fork OPEN:/lfcs-nat-1.txt
  ```

  `fork` makes socat handle each new connection in a child process so
  it keeps listening (vs a single bare `nc` which exits after one
  client). `reuseaddr` avoids `Address already in use` if restarted
  quickly.
- Verify locally on node2 first: `curl 127.0.0.1:18601` →
  `NAT-1-NODE2`.

### Part 2 (node1): custom NAT chain + DNAT for locally-originated connections

Key distinction that trips people up: DNAT for traffic **originating on
the firewall/NAT box itself** (e.g. `curl` run on node1 targeting
node1's own IP) must go through the **`OUTPUT`** chain of the `nat`
table, not `PREROUTING`. `PREROUTING` only sees packets arriving from
*other* hosts/interfaces — locally generated packets never pass through
it (they're born already past that hook).

```bash
# 1. Create the custom chain in the nat table
iptables -t nat -N LFCSNAT

# 2. Add the DNAT rule inside the custom chain
iptables -t nat -A LFCSNAT -p tcp -d 192.168.56.11 --dport 18601 \
    -j DNAT --to-destination 192.168.56.12:18601

# 3. Jump into the custom chain from the chain that actually sees the
#    traffic for locally-originated connections: OUTPUT
iptables -t nat -A OUTPUT -p tcp -d 192.168.56.11 --dport 18601 \
    -j LFCSNAT
```

- If the `curl` instead originates from a *different* host (not
  node1 itself) going *through* node1 acting as a router, the jump
  target would be `PREROUTING` instead of `OUTPUT` — same `LFCSNAT`
  chain, different hook. Know both patterns; the exam can specify
  either "locally originated" or "forwarded" traffic.
- `-d 192.168.56.11` matches the **original destination** (node1's own
  address) before translation; `--to-destination` is the NAT'd target.
- Order matters: create the chain (`-N`) before adding rules to it
  (`-A LFCSNAT ...`), and the jump rule in `OUTPUT`/`PREROUTING` must
  reference the chain by name after it exists.

### Return traffic: why SNAT/MASQUERADE is also usually needed here

With a plain DNAT-only setup, node2 sees the connection arriving with
node1's real source IP (192.168.56.11) and tries to reply directly to
it — this *usually* still works fine for the OUTPUT/locally-originated
case because the kernel's conntrack on node1 recognizes the return
packet and un-translates it back through the same `nat` table
bookkeeping before the `curl` process sees it (no extra SNAT rule
required in this specific pattern, unlike router-in-the-middle
PREROUTING NAT where asymmetric routing can be a problem). Still worth
testing both directions and adding a MASQUERADE rule on the outbound
path if the return path doesn't naturally route back through node1:

```bash
iptables -t nat -A POSTROUTING -p tcp -d 192.168.56.12 --dport 18601 -j MASQUERADE
```

### Enabling IPv4 forwarding

Needed whenever node1 is expected to forward/route packets on behalf of
another host (not strictly required just for the OUTPUT/local-origin
DNAT case above, but the exercise asks for it explicitly and it's a
near-universal companion setting for any NAT/router task):

```bash
# runtime only — lost on reboot
sysctl -w net.ipv4.ip_forward=1
# or
echo 1 > /proc/sys/net/ipv4/ip_forward

# persistent
echo "net.ipv4.ip_forward = 1" >> /etc/sysctl.conf
sysctl -p
```

Verify:

```bash
sysctl net.ipv4.ip_forward
# net.ipv4.ip_forward = 1
```

### Verifying and inspecting rules

```bash
iptables -t nat -L -v -n              # list all nat-table chains/rules
iptables -t nat -L LFCSNAT -v -n      # list just the custom chain
iptables -t nat -L OUTPUT -v -n       # confirm the jump rule is present
```

- `-n` avoids slow DNS/service-name resolution in the output.
- `-v` shows packet/byte counters per rule — useful to confirm a rule
  is actually being hit (`0 packets` after a test `curl` means the
  match criteria are wrong, e.g. wrong `-d`/`--dport`, or traffic isn't
  taking the path you think).

### Persisting iptables rules across reboot

`iptables` rules set via the CLI are runtime-only by default (same
spirit as `setenforce`/`setsebool` without `-P` elsewhere in these
notes) — they vanish on reboot unless saved:

```bash
# Debian/Ubuntu
apt install iptables-persistent
netfilter-persistent save

# RHEL/CentOS/Rocky
iptables-save > /etc/sysconfig/iptables
systemctl enable iptables
```

### Gotchas / exam traps

- Custom chains are **not** automatically consulted — they only fire
  if something jumps to them (`-j LFCSNAT` from a built-in chain).
  Creating `LFCSNAT` with `-N` and adding the DNAT rule inside it does
  nothing by itself until `OUTPUT` (or `PREROUTING`) references it.
- `OUTPUT` vs `PREROUTING` for DNAT is the single most common mix-up:
  **locally generated** packets (this exercise, `curl` run on node1
  itself) → `OUTPUT`. Packets **arriving from elsewhere to be routed
  through** node1 → `PREROUTING`.
- Forgetting `net.ipv4.ip_forward=1` silently breaks routed (not
  locally-originated) NAT scenarios — the kernel drops anything it
  would otherwise forward.
- Trailing newline in a "serve exact content" file is an easy way to
  fail an otherwise-correct validator; use `echo -n` or `printf` when
  creating the test file.
- `-d` in the NAT rule must match the **pre-NAT** destination (i.e. the
  IP the client actually connects to), not the backend's IP.

## nftables (successor to iptables)

One tool (`nft`) and one kernel engine (nf_tables) replacing iptables,
ip6tables, arptables, and ebtables. Default firewall framework on modern
RHEL and Debian — and as noted above, modern `iptables` binaries are
often just a compatibility shim on top of it.

### Concepts mapped from iptables

- **Tables** — arbitrary names (not fixed filter/nat/mangle), and belong
  to an address **family**: `ip` (v4), `ip6`, `inet` (v4+v6 dual-stack —
  prefer this for filtering), `arp`, `bridge`, `netdev`.
- **Chains** — **no built-ins exist**. You create *base chains* bound to
  a hook with a priority and policy. No base chain on a hook = nothing
  is filtered there.
- **Hooks** — `prerouting`, `input`, `forward`, `output`, `postrouting`
  (same packet-flow positions as the iptables chains of those names).
- **Priority** — lower runs earlier. Conventions: NAT prerouting `-100`,
  filter `0`, NAT postrouting `100`.
- **Rules** — expression syntax instead of flags: `tcp dport 22 accept`
  rather than `-p tcp --dport 22 -j ACCEPT`.

### Building a basic stateful firewall

```bash
nft add table inet filter
nft add chain inet filter input '{ type filter hook input priority 0; policy drop; }'
nft add rule inet filter input ct state established,related accept
nft add rule inet filter input iif "lo" accept
nft add rule inet filter input tcp dport 22 accept
nft add rule inet filter input tcp dport { 80, 443 } accept
```

Same lockout ritual as iptables: get the `established,related` + SSH
rules in before relying on the `policy drop` (or create the chain with
`policy accept` first and switch to drop last).

### Listing, deleting, flushing

```bash
nft list ruleset                        # everything
nft list table inet filter
nft -a list chain inet filter input     # -a shows rule handles
nft delete rule inet filter input handle 7
nft flush chain inet filter input
nft flush ruleset                       # nuke everything (careful)
nft delete table inet filter
```

Rules are deleted by **handle** (shown with `-a`), not by respecifying
the rule text.

### NAT equivalents (mirror of the iptables LFCSNAT exercise above)

```bash
nft add table ip nat

# locally-originated DNAT (= iptables nat OUTPUT case):
nft add chain ip nat output '{ type nat hook output priority -100; }'
nft add rule ip nat output ip daddr 192.168.56.11 tcp dport 18601 \
    dnat to 192.168.56.12:18601

# router-style DNAT (= PREROUTING case):
nft add chain ip nat prerouting '{ type nat hook prerouting priority -100; }'
nft add rule ip nat prerouting tcp dport 80 dnat to 192.168.56.12:8080

# masquerade outbound (= POSTROUTING case):
nft add chain ip nat postrouting '{ type nat hook postrouting priority 100; }'
nft add rule ip nat postrouting oif "eth0" masquerade
```

The OUTPUT-vs-PREROUTING logic for locally-originated vs routed traffic
is identical to iptables — only the syntax changes. `ip_forward` is
still required for routed scenarios (see NAT section above).

### Sets — the headline convenience feature

```bash
# anonymous set, inline:
nft add rule inet filter input tcp dport { 22, 80, 443 } accept

# named set, maintainable without touching rules:
nft add set inet filter allowed_tcp '{ type inet_service; }'
nft add element inet filter allowed_tcp '{ 22, 80, 443 }'
nft add rule inet filter input tcp dport @allowed_tcp accept
```

### Persistence

```bash
nft list ruleset > /etc/nftables.conf   # keep the shebang/flush header, see below
systemctl enable --now nftables
```

- Debian/Ubuntu: `nftables.service` loads `/etc/nftables.conf`; the file
  conventionally starts with `#!/usr/sbin/nft -f` and `flush ruleset`.
- RHEL/Rocky: `/etc/sysconfig/nftables.conf` (often `include`s files).
- Syntax-check a saved file without applying: `nft -c -f /etc/nftables.conf`.

### Migrating from iptables knowledge

```bash
iptables-translate -A INPUT -p tcp --dport 22 -j ACCEPT
# nft add rule ip filter INPUT tcp dport 22 counter accept

iptables-restore-translate -f saved-iptables-rules.txt   # whole ruleset
```

Great learning shortcut: write the rule you know in iptables syntax, let
the translator show the nft form.

### Gotchas / exam traps

- The shell eats `{ } ;` — **single-quote** chain/set definitions
  (`'{ type filter hook input priority 0; policy drop; }'`).
- No base chain = no filtering on that hook at all (everything passes);
  a base chain with `policy drop` and no rules = everything on that hook
  drops. Both directions of this surprise people.
- `inet` family covers v4+v6 in one table — avoids the iptables-era
  duplicate ip6tables ruleset. Use it for filter tables; NAT historically
  wants family `ip`/`ip6` (inet NAT works on newer kernels, but `ip` is
  the safe exam choice).
- Rules delete by handle (`-a` to see them), not by rule text.
- Don't manage the same host with raw `nft` and `iptables`
  simultaneously — the iptables-nft shim's rules show up in
  `nft list ruleset` and it gets confusing fast.
